## 一、录制前准备（一次性，务必先做完）

### 1. 把数据库切到 `test`

演示用的 `orders` / `users` / `products` 三张表都在 **`test` 库**里。
而你当前 `.env` 里是 `DB_NAME=text`，**必须先改**，否则界面连不上表。

用记事本打开项目根目录的 `.env`，改成：

```ini
DB_NAME=test
```

> 也可以录屏时通过「设置 → Database」改成 `test`（顺便展示设置界面），但为了录制流畅，建议提前改好。

### 2. 确认测试数据与索引状态

在项目根目录执行：

```bash
.venv/Scripts/python.exe -c "
import pymysql
from sql_coach.config import load_config
from sql_coach.models import Config
load_config(env_path='.env'); b=Config.from_env()
c=pymysql.connect(host=b.db.host,port=b.db.port,user=b.db.user,password=b.db.password,database='test')
cur=c.cursor()
for t in ('orders','users','products'):
    cur.execute(f'SELECT COUNT(*) FROM {t}'); print(f'{t} 行数:', cur.fetchone()[0])
cur.execute('SHOW INDEX FROM orders'); print('orders 索引:', sorted({r[2] for r in cur.fetchall()}))
c.close()
"
```

期望输出：`orders 行数: 100000`、`users 行数: 10000`、`products 行数: 1000`、`orders 索引: ['PRIMARY', 'user_id']`

**如果索引里出现了 `idx_orders_status` 或 `idx_orders_amount`，要先删掉**，否则演示索引实测时会显示"索引已存在"：

```sql
DROP INDEX idx_orders_status ON orders;
DROP INDEX idx_orders_amount ON orders;
```

### 3. 确认 NL 模式可用（第 5 幕）

第 5 幕要现场生成 SQL，**先在命令行跑一次确认**：

```bash
.venv/Scripts/python.exe -c "
from sql_coach.config import load_config
from sql_coach.models import Config
from sql_coach.coach import SQLCoach
load_config(env_path='.env'); b=Config.from_env()
coach=SQLCoach(b); coach.connect()
r=coach.generate_sql('查询每个城市的用户数量')
print(r.generated_sql, '| 行数:', len(r.rows))
coach.close()
"
```

期望输出：`SELECT city, COUNT(*) FROM users GROUP BY city; | 行数: 5`

> 首次运行会加载 jieba 词典（约 0.7 秒），**录制前先跑一次**，让词典进缓存，现场就不会卡顿。

## 二、分镜脚本

### 🎬 第 1 幕｜启动（0:00 – 0:20）

**操作**：双击项目根目录的 `sql-coach-gui.exe`

**画面**：窗口打开，标题栏显示 `DB: 已连接`，工具栏最左侧有一个模式下拉框（当前为「优化模式」）

**解说词**：
> 这是我做的一个 MySQL 慢查询优化系统，叫 SQL Coach。它输入一条 SQL，会自动连数据库执行 EXPLAIN、分析执行计划，给出优化建议，并且实测优化前后的性能对比。双击这个 exe 就能直接用。

---

### 🎬 第 2 幕｜简单 SQL 走本地引擎（0:20 – 1:05）★核心

**操作**：
1. 在左侧输入框粘贴下面这条 SQL
2. 按 `Ctrl + Enter`（或点「🔍 分析」）

```sql
SELECT * FROM orders WHERE status='pending'
```

**画面**（右侧报告区依次出现）：
- 顶部徽章：**优化引擎：本地规则　复杂度：简单 (0)**
- 执行计划表格：`type = ALL`（红色高亮）、`rows ≈ 100000`
- ⚠️ 发现 2 个问题：`status 缺少索引`、`使用了 SELECT *`
- 索引建议：`CREATE INDEX idx_orders_status ON orders(status);`
- 性能对比柱状图

**解说词**：
> 先看一条简单查询。它自动连上数据库执行了 EXPLAIN，可以看到执行计划里 type 是 ALL，也就是全表扫描，扫了十万行。
>
> 工具识别出两个问题：`status` 字段没有索引，以及用了 `SELECT *`。并给出了建索引的语句。
>
> 注意右上角这两个标签——**优化引擎是"本地规则"，复杂度是"简单"**。因为这条 SQL 结构很简单，我用自己写的本地规则引擎就分析完了，**毫秒级返回，不需要联网、也不消耗大模型额度**。

---

### 🎬 第 3 幕｜复杂 SQL 走 AI（1:05 – 1:50）

**操作**：清空输入框，粘贴下面这条，再按 `Ctrl + Enter`

```sql
SELECT u.city, COUNT(*) AS cnt,
       ROW_NUMBER() OVER (ORDER BY COUNT(*) DESC) AS rn
FROM users u
JOIN orders o ON u.id = o.user_id
JOIN products p ON p.id = o.id
WHERE u.city IN ('北京','上海')
GROUP BY u.city
ORDER BY cnt DESC
```

**画面**：
- 顶部徽章：**优化引擎：deepseek　复杂度：复杂 (12)**
- 分析过程中能看到 AI 流式输出的过程（等几秒）

**解说词**：
> 再看这条复杂一点的：三张表 JOIN、还有窗口函数和聚合。
>
> 可以看到复杂度评分是 12 分，判为"复杂"，**这时候才交给 AI 大模型处理**。
>
> 这就是这个项目的核心思路：**不是所有 SQL 都值得调用大模型**。简单和中等的 SQL 用本地规则秒出结果，只有真正复杂的才走 AI——既快又省。

---

### 🎬 第 4 幕｜索引实测（1:50 – 3:00）★★最大亮点

**操作**：
1. 打开菜单「设置 → 打开设置...」
2. 勾选 **「索引实测：实测索引收益」**
3. 点「💾 保存到 .env」，关闭设置
4. 输入下面这条 SQL，按 `Ctrl + Enter`

```sql
SELECT * FROM orders WHERE amount>999.5
```

**画面**：
- 报告底部出现 **📈 索引实测** 一节：
  ```
  建索引前:  0.041s
  建索引后:  0.001s
  实测提速: 45.9x
  结论: 索引有效（实测提速 45.9x），建议采纳
  命中率: 0.05%（50/99947 行）
  ```

**解说词**：
> 接下来是我觉得最有意思的一个功能——**索引实测**。
>
> 一般的工具只能"建议你加索引"，但到底加了这个索引有没有用，没人验证。我做的这个会**临时把索引真的建出来，重新测一遍，然后再回滚删掉**。
>
> 这条查询命中的行很少，所以实测提速是 **45 倍**，结论是"建议采纳"。

**操作（对比）**：再粘贴这一条，`Ctrl + Enter`

```sql
SELECT * FROM orders WHERE status='pending'
```

**画面**：
```
建索引前:  0.267s
建索引后:  0.263s
实测提速: 0.98x
结论: 索引收益有限（实测提速 0.98x，低于阈值 1.30x，命中率约 33.2%），不建议创建
```

**解说词**：
> 再看这条，同样是没索引、同样会提示"建议建索引"，但实测下来**几乎没有提升**，只有 0.98 倍，所以工具明确说"**不建议创建**"。
>
> 原因是这条查询命中了 33% 的行——**选择性太低**，即便用上索引也要回表三万多行，成本和全表扫描差不多。
>
> 我在十万行的表上专门做过一次选择性扫描，发现**索引在命中率超过大约 5% 之后基本就失效了**。所以给工具加了收益守卫：实测提速低于 1.3 倍就明确说不建议建。这也是我做这个项目的一个真实发现——**很多资料说"加索引提速 50 到 100 倍"，其实只在选择性足够高的时候才成立。**

### 🎬 第 5 幕｜自然语言转 SQL（3:00 – 3:50）★新增亮点

**操作**：
1. 点工具栏最左侧的模式下拉，切换到 **「自然语言模式」**
   （左侧变成「自然语言查询」输入框，右侧变成「生成的 SQL」+「查询结果」）
2. 在左侧输入框粘贴下面这句话，按 `Ctrl + Enter`（或点「✨ 生成 SQL」）

```
查询每个城市的用户数量
```

**画面**（右侧依次出现）：
- 「生成的 SQL」区：`SELECT city, COUNT(*) FROM users GROUP BY city;`
- 「查询结果」表格：标题显示 **查询结果（5 行）**，表格里是 5 个城市及计数
- 状态栏：`⚠ 有 1 条提示 | 结果 5 行（请查看提示确认是否符合预期）`
  （提示内容是"查询无 WHERE 且无 LIMIT，可能返回大量数据"，属正常提醒）

**解说词**：
> 前面演示的都是"已经会写 SQL"的人用的。但实际工作中，很多人只是想查个数据，却不会写 SQL。
>
> 所以我还做了**自然语言转 SQL**——**纯本地算法，不调用任何 AI**。我直接输入一句中文："查询每个城市的用户数量"，它就自动生成了 SQL，并且**当场执行、把结果表格展示出来**。
>
> 注意它不是简单的模板套壳：它会先读数据库的真实表结构，把"用户"映射到 `users` 表、"城市"映射到 `city` 列，还识别出"每个"是分组、"数量"是计数，最后拼成 `GROUP BY city`。

**操作（补充对比，可选）**：再输入一句，`Ctrl + Enter`

```
查询最近10条订单
```

**画面**：生成 `SELECT * FROM orders ORDER BY created_at DESC LIMIT 10;`，结果表格 10 行

**解说词**：
> 再换一句："查询最近10条订单"。它识别出"最近"要按时间倒序、"10条"是 LIMIT 10，生成 SQL 并返回结果。
>
> 如果生成的结果不放心，这里有个「**🔍 送入优化模式**」按钮——一键把 SQL 送进刚才的优化流程里，检查有没有性能问题。**两个模式是打通的。**

**操作（演示连通，可选）**：点一下「🔍 送入优化模式」，界面自动切回优化模式并填入 SQL

```sql
SELECT u.city, COUNT(*) AS cnt,

JOIN products p ON p.id = o.id

GROUP BY u.city
ORDER BY cnt DESC
```


**④ 低选择性 → 索引实测"不建议创建"**（优化模式）
```sql
SELECT * FROM orders WHERE status='pending'
```

## 五、注意事项

1. **别录首次启动**：onefile 第一次启动要解压到临时目录，约 5-10 秒且可能杀软弹窗，先预热一次。
2. **索引实测必须真的连库**：模拟模式下该功能会自动跳过（这是设计如此）。
3. **索引实测会短暂改动数据库**：它只创建自己建议的那一个索引，并在 `finally` 里回滚；如果演示中断，可以用 `SHOW INDEX FROM orders` 确认，必要时手动 `DROP INDEX`。
4. **第 3 幕依赖 AI 可用**：如果网络或 API Key 有问题，这一步会降级并提示失败——录制前先跑一次确认能出结果。
5. **第 5 幕 NL 模式纯本地**：不依赖网络，但**首次生成会加载 jieba 词典**（约 0.7 秒），录制前先跑一次预热。若生成的 SQL 与预期略有出入，说明输入措辞不同，改用清单里的原句即可。
6. **如果第 4 幕显示"索引已存在，无需创建"**：说明之前演示留下的索引没删干净，执行准备步骤里的 `DROP INDEX` 即可。
7. **语速**：第 2、4、5 幕是重点，可以讲慢一点；第 3 幕 AI 要等几秒，正好用来解说分流策略，不会冷场。
8. **若总时长超限**：优先保留第 2 幕（本地引擎）、第 4 幕（索引实测）、第 5 幕（自然语言）——这三幕最能体现项目的差异化；第 3 幕可压缩为一句话带过。
