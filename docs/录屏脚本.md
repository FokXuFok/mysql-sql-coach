> 总时长约 4 分 10 秒。按分镜顺序操作即可，解说词可直接照念。
>
> **本版新增第 5 幕「自然语言转 SQL」**（3:00 – 3:50）。若时间紧张，可把第 3 幕压缩或跳过，其余顺序不变。
>
> **v2 修订说明（均据实机跑通后修订）**
> 1. **修正第 3 幕 SQL 的 JOIN 错误**：原写法 `ON p.id = o.id` 把 products 主键和 orders 主键关联，而 `orders` 表并没有 `product_id` 列，实跑会导致 AI 判为"JOIN 条件错误"、并改写出一条引用不存在列的 SQL，进而**性能对比 3 次全部失败、索引实测也失败**。
> 2. 第 3 幕**并没有"AI 流式输出"画面**（后台分析线程未接 `on_chunk`），原描述与实现不符，已改为状态栏阶段文字。
> 3. 补充**关键前置：录制前必须把索引实测关掉**，否则第 2 幕不是"本地规则秒出"而是十几秒。
> 4. 补充**索引残留的正确清理方法**（`idx_orders_user_id` 被外键占用，直接 `DROP INDEX` 会报 1553）。
> 5. 修正**缩放结论**：本项目是 Qt6 高 DPI 感知程序，125% 下界面按 1.25 倍**原生渲染**，**不会糊**，字号反而更适合视频观看。
> 6. 若干实测耗时/数值按真实结果更新，并标注哪些是"参考值、随机器波动"。
> 7. 补充**录制前要先点掉「环境自检」弹窗**、以及第 5 幕会弹「生成提示」小窗等现场容易误判的现象。
>
> **v3 修订说明（第 4 幕索引实测"没出现对比"的根因）**
> 实测复现了一个应用缺陷：设置里点「💾 保存到 .env」**在本次运行内不生效**。原因在 `sql_coach/config.py` 的 `load_env_file()`——它只填"环境变量里还没有的键"，不覆盖已有值；而程序启动时已经把 `.env` 的 `MEASURE_INDEX` 读进了环境变量，所以保存后重载拿到的还是旧值。
> **因此不能把 `.env` 写成 `MEASURE_INDEX=false`**（那样第 4 幕勾选保存后内存里仍是 `false`，右侧不会出现「📈 索引实测」）。正确做法是**把该行整行删掉**，详见「准备步骤 2」。
> 该缺陷**已在源码中修复**（见「注意事项 11」，全量 566 项测试通过）；但现成的 `sql-coach-gui.exe` 里仍是旧代码，所以录制时**仍建议按"删掉该行"操作**，两种 exe 状态都能正常出索引实测。

## 一、录制前准备（一次性，务必先做完）

### 0. 先启动一次，点掉「环境自检」

程序启动时会做环境自检，**只要有任一项不 ok 就会弹出「环境自检」对话框**——把它录进第 1 幕很难看。

先启动一次 `sql-coach-gui.exe`，在自检窗口上点「跳过」（它会在 `C:\Users\<你>\.sql-coach\.skip_diagnostics` 写入标记，之后不再弹），然后关掉程序。

> 本机该标记文件**目前并不存在**，所以这一步不能省。

### 1. 确认数据库指向 `test`

演示用的 `orders` / `users` / `products` 三张表都在 **`test` 库**里。

打开项目根目录的 `.env` 核对这一行（**当前已经是 `test`，无需修改**）：

```ini
DB_NAME=test
```

> 若这里被改成了 `text` 之类的错值，界面会连不上表，必须先改回来。
> 也可以录屏时通过「设置 → Database」改成 `test`（顺便展示设置界面），但为了录制流畅，建议提前改好。

### 2. 关键：让「索引实测」在第 2、3 幕是关的，且第 4 幕能立即打开

第 4 幕的剧情是"现场在设置里勾选索引实测"，也就是说**第 2、3 幕必须处于关闭状态**。索引实测开着时，每条 SQL 都会额外走上"建索引 → 复测 → 回滚"，第 2 幕会从"本地规则秒出"变成十几秒，和第 2 幕的解说词直接冲突。

**做法：把 `.env` 里的 `MEASURE_INDEX` 整行删掉**（不是写成 `false`）：

```ini
# 不要保留下面这一行；MEASURE_INDEX 这一行直接删除
# MEASURE_INDEX=false      ← 错误做法，会导致第 4 幕看不到索引实测
```

原理与实测结果（在实机上复现过）：

| `.env` 的写法 | 启动时 | 第 4 幕在设置里勾选并保存后 | 第 4 幕效果 |
|---|---|---|---|
| `MEASURE_INDEX=false` | false | **仍是 false**（被"不覆盖已有键"挡住） | ❌ 右侧没有「📈 索引实测」 |
| **删掉这一行** | false（取默认值） | **true** | ✅ 索引实测正常出现 |

> 为什么删掉就行：环境变量里原本没有这个键，第 4 幕保存后 `.env` 新写入的 `MEASURE_INDEX=true` 就能被正常读入。
> **每次重录第 2、3 幕之前，都要把这一行再删掉**——第 4 幕会把它写成 `true`，留着会让第 2 幕变慢。
>
> 想让「设置里改配置立即生效」不再是个坑，可以顺手修掉这个缺陷（3 行代码），见「注意事项 11」。
>
> ⚠️ **别改错文件**：程序读取的是"**和 exe 同目录**"的 `.env`。
> - **本次录制用的是竞赛包那份**：`…\05_作品相关代码\可运行程序\sql-coach-gui.exe` → 读 `可运行程序\.env`（**已按上面的做法删掉 `MEASURE_INDEX` 行**）；
> - 若改双击项目根目录的 `sql-coach-gui.exe` → 读 `D:\mysql-sql-coach\.env`（**同样已删掉该行**）。
>
> **用哪个 exe，就改哪一份 `.env`**——两份互相独立，目前两份都已处理为"没有 `MEASURE_INDEX` 这一行"。

### 3. 确认测试数据与索引状态

在项目根目录执行：

```bash
.venv/Scripts/python.exe -c "
import pymysql
from sql_coach.config import load_config
from sql_coach.models import Config
load_config(env_path='.env'); b=Config.from_env()
print('MEASURE_INDEX =', b.measure_index)
c=pymysql.connect(host=b.db.host,port=b.db.port,user=b.db.user,password=b.db.password,database='test')
cur=c.cursor()
for t in ('orders','users','products'):
    cur.execute(f'SELECT COUNT(*) FROM {t}'); print(f'{t} 行数:', cur.fetchone()[0])
cur.execute('SHOW INDEX FROM orders'); print('orders 索引:', sorted({r[2] for r in cur.fetchall()}))
cur.execute('SELECT CONSTRAINT_NAME FROM information_schema.TABLE_CONSTRAINTS WHERE TABLE_SCHEMA=%s AND TABLE_NAME=%s AND CONSTRAINT_TYPE=%s', ('test','orders','FOREIGN KEY'))
print('orders 外键:', sorted(r[0] for r in cur.fetchall()))
c.close()
"
```

期望输出：

```
MEASURE_INDEX = False
orders 行数: 100000
users 行数: 10000
products 行数: 1000
orders 索引: ['PRIMARY', 'user_id']
orders 外键: ['orders_ibfk_1']
```

**如果索引里出现了 `idx_orders_status` 或 `idx_orders_amount`**（上次演示的残留），删掉：

```sql
DROP INDEX idx_orders_status ON orders;
DROP INDEX idx_orders_amount ON orders;
```

**如果索引里出现了 `idx_orders_user_id`**：这是**索引实测回滚失败**留下的（`orders.user_id` 的外键抢用了这个索引，删它会报 `1553 Cannot drop index 'idx_orders_user_id': needed in a foreign key constraint`）。**不能直接 DROP**，正确恢复步骤如下：

```sql
ALTER TABLE orders DROP FOREIGN KEY orders_ibfk_1;   -- 1. 先摘掉外键
CREATE INDEX user_id ON orders(user_id);             -- 2. 重建原名索引
DROP INDEX idx_orders_user_id ON orders;             -- 3. 现在才能删
ALTER TABLE orders ADD CONSTRAINT orders_ibfk_1 FOREIGN KEY (user_id) REFERENCES users(id);  -- 4. 挂回外键
```

恢复后 `SHOW INDEX FROM orders` 应只剩 `PRIMARY` 和 `user_id`。

> 为什么会残留：索引实测在 `finally` 里回滚，但若它建的索引恰好被外键占用，`DROP` 会失败，索引就留在库里了（第 4 幕也可能再次遇到，见「注意事项 3」）。

### 🎬 第 2 幕｜简单 SQL 走本地引擎（0:20 – 1:05）★核心

**操作**：
1. 在左侧输入框粘贴下面这条 SQL
2. 按 `Ctrl + Enter`（或点「🔍 分析」）

```sql
SELECT * FROM orders WHERE status='pending'
```

**画面**（右侧报告区依次出现）：
- 顶部徽章：**优化引擎：本地规则　复杂度：简单 (0)**
- 执行计划表格：`type = ALL`（红色高亮）、`rows ≈ 100000`
- ⚠️ 发现 2 个问题：`status 缺少索引`、`使用了 SELECT *`
- 索引建议：`CREATE INDEX idx_orders_status ON orders(status);`
- 性能对比柱状图
- 状态栏：`完成 | 本地规则 | 耗时 5.3s`（实测值，含下面说的性能对比计时）

**解说词**：
> 先看一条简单查询。它自动连上数据库执行了 EXPLAIN，可以看到执行计划里 type 是 ALL，也就是全表扫描，扫了十万行。
>
> 工具识别出两个问题：`status` 字段没有索引，以及用了 `SELECT *`。并给出了建索引的语句。
>
> 注意右上角这两个标签——**优化引擎是"本地规则"，复杂度是"简单"**。因为这条 SQL 结构很简单，我用自己写的本地规则引擎就分析完了，**不联网、也不消耗大模型额度**；界面上那几秒耗时主要来自后面性能对比的实测计时。

> ⚠️ 如果这一步是"十几秒"，或者报告底部出现了「📈 索引实测」，说明准备步骤 2 没做（`MEASURE_INDEX` 还是 `true`）。

### 🎬 第 3 幕｜复杂 SQL 走 AI（1:05 – 1:50）

> **v2 已修正**：原 SQL 的 `JOIN products p ON p.id = o.id` 是错的——它把 products 的主键和 orders 的主键关联，而 `orders` 表里根本没有 `product_id` 列。实跑会出现：AI 把它判为"JOIN 条件错误"，并改写出一条引用不存在列的 SQL，导致**性能对比 3 次全部失败、索引实测也失败**。下面这条已实测通过。

**操作**：清空输入框，粘贴下面这条，再按 `Ctrl + Enter`

```sql
SELECT u.city, COUNT(*) AS cnt,
       ROW_NUMBER() OVER (ORDER BY COUNT(*) DESC) AS rn
FROM users u
JOIN orders o ON u.id = o.user_id
WHERE u.city IN ('北京','上海')
  AND o.amount > (SELECT AVG(price) FROM products)
GROUP BY u.city
ORDER BY cnt DESC
```

**画面**：
- 顶部徽章：**优化引擎：deepseek　复杂度：复杂 (13)**
- 执行计划里能看到三张表：`users`（type=ALL）、`orders`（type=ref，key=user_id）、`products`（SUBQUERY）
- 状态栏依次变成：`正在解析 SQL ...` → `正在执行 EXPLAIN ...` → `AI 分析中 ...` → `性能对比中 ...`
- 等约 **15–20 秒**（实测 16.2 秒）后报告一次性出现

**解说词**：
> 再看这条复杂一点的：跨了三张表——`users` 和 `orders` 做 JOIN，`products` 出现在子查询里——还带窗口函数和聚合。
>
> 可以看到复杂度评分是 13 分，判为"复杂"，**这时候才交给 AI 大模型处理**。
>
> 这就是这个项目的核心思路：**不是所有 SQL 都值得调用大模型**。简单和中等的 SQL 用本地规则秒出结果，只有真正复杂的才走 AI——既快又省。

> **两点注意，免得现场误判：**
> 1. **没有"AI 流式输出"效果**：后台分析线程只上报阶段、不转发流式分片，画面上只有状态栏那几行阶段文字，报告是一次性出现的。等 AI 的这十几秒正好用来念上面那段解说词，不会冷场。
> 2. **AI 每次建议的措辞都不同**（大模型非确定性），别把具体句子背成台词。如果这次 AI 恰好把 SQL 改写成了有问题的版本、导致「📊 性能对比」缺失，**直接重录第 3 幕**即可，或改用下面的备用 SQL。

**备用 SQL（若上面那条连续两次表现异常）**：去掉子查询的版本，复杂度 **10 分**，同样判为"复杂 → 走 AI"：

```sql
SELECT u.city, COUNT(*) AS cnt,
       ROW_NUMBER() OVER (ORDER BY COUNT(*) DESC) AS rn
FROM users u
JOIN orders o ON u.id = o.user_id
WHERE u.city IN ('北京','上海')
GROUP BY u.city
ORDER BY cnt DESC
```

> 用备用 SQL 时，「解说词全文」里"跨了三张表"改成"两张表 JOIN、还有窗口函数和聚合"，徽章分数念 10 分。

### 🎬 第 4 幕｜索引实测（1:50 – 3:00）★★最大亮点

**操作**：
1. 打开菜单「设置 → 打开设置...」
2. 勾选 **「索引实测：实测索引收益」**
3. 点「💾 保存到 .env」，关闭设置
4. 输入下面这条 SQL，按 `Ctrl + Enter`

```sql
SELECT * FROM orders WHERE amount>999.5
```

**画面**（报告**最底部**的「📈 索引实测」一节；参考值，随机器波动）：
```
建索引前:  0.041s
建索引后:  0.001s
实测提速: 45.9x
结论: 索引有效（实测提速 45.9x），建议采纳
命中率: 0.05%（50/99947 行）
```

> 这一节在报告**最底部**，记得把右侧报告区**滚到最下面**再念解说词，否则镜头里看不到它。

**解说词**：
> 接下来是我觉得最有意思的一个功能——**索引实测**。
>
> 一般的工具只能"建议你加索引"，但到底加了这个索引有没有用，没人验证。我做的这个会**临时把索引真的建出来，重新测一遍，然后再回滚删掉**。
>
> 这条查询命中的行很少，所以实测提速是 **45 倍**，结论是"建议采纳"。

**操作（对比）**：再粘贴这一条，`Ctrl + Enter`

```sql
SELECT * FROM orders WHERE status='pending'
```

**画面**（参考值；本次实测录到的是 **0.92x**，与下面 0.98x 同量级）：
```
建索引前:  0.267s
建索引后:  0.263s
实测提速: 0.98x
结论: 索引收益有限（实测提速 0.98x，低于阈值 1.30x，命中率约 33.2%），不建议创建
```

> 具体小数每次都会变，**但"不建议创建"这个结论和 1.30x 这个阈值是稳定的**，别把小数背成台词。

**解说词**：
> 再看这条，同样是没索引、同样会提示"建议建索引"，但实测下来**几乎没有提升**，只有 0.98 倍，所以工具明确说"**不建议创建**"。
>
> 原因是这条查询命中了 33% 的行——**选择性太低**，即便用上索引也要回表三万多行，成本和全表扫描差不多。
>
> 我在十万行的表上专门做过一次选择性扫描，发现**索引在命中率超过大约 5% 之后基本就失效了**。所以给工具加了收益守卫：实测提速低于 1.3 倍就明确说不建议建。这也是我做这个项目的一个真实发现——**很多资料说"加索引提速 50 到 100 倍"，其实只在选择性足够高的时候才成立。**

## 三、输入清单（直接复制）

**② 复杂查询 → AI**（优化模式）★v2 已修正
```sql
SELECT u.city, COUNT(*) AS cnt,
       ROW_NUMBER() OVER (ORDER BY COUNT(*) DESC) AS rn
FROM users u
JOIN orders o ON u.id = o.user_id
WHERE u.city IN ('北京','上海')
  AND o.amount > (SELECT AVG(price) FROM products)
GROUP BY u.city
ORDER BY cnt DESC
```

## 四、解说词全文（连续版，可直接念）

> 这是我做的一个 MySQL 慢查询优化系统，叫 SQL Coach。输入一条 SQL，它会自动连数据库执行 EXPLAIN、分析执行计划，给出优化建议，并且实测优化前后的性能对比。
>
> 先看一条简单查询。它识别出 `status` 没有索引、并且用了 `SELECT *`，给出建索引的语句。注意这里显示"优化引擎是本地规则、复杂度是简单"——因为这条 SQL 结构简单，我用自己写的本地规则引擎就分析完了，不需要联网、也不消耗大模型额度；界面上那几秒主要花在性能对比的实测计时上。
>
> 再看一条复杂的：跨三张表——`users` 和 `orders` 做 JOIN，`products` 在子查询里——还带窗口函数。复杂度评分 13 分，判为"复杂"，这时候才交给 AI。这就是核心思路——**不是所有 SQL 都值得调大模型**。
>
> 最有意思的是**索引实测**。一般工具只能建议你加索引，但加了到底有没有用没人验证。我这个会**临时把索引真的建出来、重新测一遍、再回滚删掉**。这条查询命中行少，实测提速 45 倍，建议采纳；换成命中 33% 的那条，实测只有 0.98 倍，工具就明确说**不建议创建**——因为选择性太低，索引基本没用。我还专门做过选择性扫描，发现**索引在命中率超过约 5% 之后就基本失效**，所以加了收益守卫：低于 1.3 倍就不建议建。
>
> 前面演示的都是会写 SQL 的人用的。所以我还做了**自然语言转 SQL**——纯本地算法，不调 AI。我输入一句中文"查询每个城市的用户数量"，它就自动读表结构、识别分组和聚合，生成 SQL 并**当场执行出结果**。生成后还能一键「送入优化模式」，检查这条 SQL 有没有性能问题。
>
> 结果可以导出成 Markdown 或 HTML 报告。项目包含 563 项自动化测试，完整源码和文档都在压缩包里。谢谢老师。

## 五、注意事项

1. **别录首次启动**：onefile 第一次启动要解压到临时目录，约 5-10 秒且可能杀软弹窗，先预热一次。
2. **`MEASURE_INDEX` 的顺序不能乱，而且写法有讲究**：录制前 `.env` 里**不要有 `MEASURE_INDEX` 这一行**（不能写 `false`，原因见「准备步骤 2」），这样第 2 幕才"本地规则秒出"；第 4 幕在设置里现场勾上并保存后会立即生效，之后 `.env` 里就是 `true`。**重录第 2、3 幕前记得再把这一行删掉。**
3. **索引实测会短暂改动数据库**：它只创建自己建议的那一个索引，并在 `finally` 里回滚。**但如果建议的索引恰好被外键占用，回滚会失败（报 1553），索引会残留在库里**——这时按「准备步骤 3」那 4 步 SQL 恢复，别直接 `DROP`。演示中断后先 `SHOW INDEX FROM orders` 确认一下。
4. **第 3 幕依赖 AI 可用**：网络或 API Key 有问题时这一步会降级并提示失败——录制前先跑一次确认能出结果。同时注意 **AI 建议是非确定性的**，每次措辞都不同，别把具体句子背成台词。
5. **第 5 幕 NL 模式纯本地**：不依赖网络，但首次生成要构建 jieba 词典（实测约 2.1 秒），录制前先跑一次预热。若生成的 SQL 与预期略有出入，说明输入措辞不同，改用清单里的原句即可。
6. **第 5 幕弹「生成提示」小窗是正常的**：只要生成的 SQL 触发了本地规则（无 WHERE / 用了 SELECT * 等）就会弹一个非模态提示窗，不影响演示；不想让它出现的话，把输入句改成带条件的（例如"查询北京的用户数量"）即可。
7. **第 3 幕没有流式字幕**：只有状态栏的阶段文字（正在解析 → 正在执行 EXPLAIN → AI 分析中 → 性能对比中），报告是一次性出现的。等 AI 的十几秒正好念解说词。
8. **如果第 4 幕显示"索引已存在，无需创建"**：说明之前演示留下的索引没删干净，按「准备步骤 3」清理。
9. **语速**：第 2、4、5 幕是重点，可以讲慢一点；第 3 幕 AI 要等 15-20 秒，正好用来解说分流策略，不会冷场。
10. **若总时长超限**：优先保留第 2 幕（本地引擎）、第 4 幕（索引实测）、第 5 幕（自然语言）——这三幕最能体现项目的差异化；第 3 幕可压缩为一句话带过。
11. **"设置里改了不生效、必须重开程序"的缺陷已修复（源码层面）**，一共三处：

    | 缺陷 | 现象 | 修复 |
    |---|---|---|
    | 保存后不重载新值 | `load_env_file()` 只填"环境里还没有的键"，`.env` 的新值被 `os.environ` 里的旧值挡住 | `load_config(..., override_env=True)`，保存后重载 |
    | **降级成"模拟模式"后永久卡住** | 启动时连库失败 → `mock=True`；保存设置时沿用了这个状态、且 `_check_db_connection()` 直接 `return`，**再也回不到真实连接**，只能关掉重开。而模拟模式下 EXPLAIN / 性能对比 / **索引实测全部按设计跳过**，所以第 4 幕永远看不到对比 | 保存后 `mock=False` + `_check_db_connection(force_retry=True)` 强制重试 |
    | 连库失败看不到原因 | `DBConnector.connect()` 把异常吞进 logger，而窗口程序没有控制台 | 新增 `last_error`，失败提示里直接显示真实错误 |

    现在「💾 保存到 .env」会**立即重载 .env 并重试数据库连接**，不需要重开程序；回归测试已补到 **569 项全部通过**。

    ⚠️ **录制用的 exe 必须重新打包才会带上这些修复**——现成的 `sql-coach-gui.exe` 里是旧代码。三种选择：

    - **重新打包（推荐）**：PyInstaller 重新生成 exe，之后设置保存即生效；
    - **不改 exe，靠规避**：把 `.env` 里的 `MEASURE_INDEX` 整行删掉（第 4 幕保存后仍能被读到），并**在录制前重开一次程序**、确认状态栏是 `DB: 已连接`；
    - **从源码运行**：`.venv\Scripts\python.exe main.py --gui`，直接就是修复后的代码（画面与 exe 完全一致）。
