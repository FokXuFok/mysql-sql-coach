# SQL Coach 项目介绍

> 一个 AI 驱动的 MySQL 慢查询优化教练：输入一条 SQL，自动分析执行计划、给出优化建议，并实测优化效果。
> 提供桌面 GUI 与命令行两种使用方式，可打包为单文件 exe 分发。

---

## 一、一句话概括

**SQL Coach 让"慢查询优化"从依赖经验的手工活，变成一条可自动执行、且结果可被实测验证的流水线。**

输入一条 SQL → 自动连 MySQL 执行 EXPLAIN → 分析执行计划 → 给出优化建议（改写后的 SQL + 索引 DDL）→ 实测优化前后性能 → 输出报告。

---

## 二、要解决的问题

MySQL 慢查询优化长期依赖工程师经验：看 EXPLAIN、判断该不该加索引、手写改写 SQL，再反复试。

现有的辅助手段各有短板：

| 方式 | 问题 |
|------|------|
| 纯人工看 EXPLAIN | 门槛高、耗时、结论不可验证 |
| 把 SQL 直接丢给大模型 | 每次要等数秒、有调用成本，而且**模型看不到你库里真实的索引情况** |
| 慢日志监控平台 | 通常只告警不给出可执行的改写方案，且需要额外部署 |

SQL Coach 的思路是：**把"能确定的事"交给本地规则引擎（毫秒级、离线、免费），把"需要推理的事"交给大模型**，并且**用真实数据库实测来验证结论**。

---

## 三、核心功能

1. **自动执行计划分析**：执行 `EXPLAIN FORMAT=JSON` 并解析成结构化结果（访问类型、命中索引、扫描行数、filesort 等）
2. **双引擎优化**
   - **本地规则引擎**：13 条规则，毫秒级返回
   - **AI 大模型**：支持 DeepSeek / OpenAI / Ollama，可切换
3. **复杂度自动分流**：按 SQL 结构特征打分，简单/中等走本地，复杂才调 AI（可配置阈值或强制指定）
4. **安全改写**：只对**能静态证明语义等价**的语句自动改写（`SELECT *` 展开为显式列、`DATE(col)='...'` 改写为范围条件）；其余一律只给建议
5. **性能实测**：同一 SQL 多次执行取最优值，对比优化前后耗时与扫描行数
6. **索引实测模式**：临时创建索引 → 复测 → **回滚**，给出该索引的**真实收益**，并判断"是否值得建"
7. **启动环境自检**：检测 `.env` / MySQL 连接 / AI 配置 / 运行环境依赖，能安全自动修复的直接修复，系统级软件只给安装指引
8. **工程配套**：报告导出（Markdown / HTML）、历史记录、一键复制、SQLite 分析缓存
9. **分发**：PyInstaller 单文件 exe，双击即用；CI 三平台并行构建

## 四、技术架构

```
main.py（智能入口）
   │
   ├─ 打包运行 / --gui ──▶ gui/（PySide6 桌面界面，薄层，不含业务逻辑）
   └─ 否则 ─────────────▶ CLI 交互模式（click + rich）

核心库 sql_coach/（与界面完全解耦，可独立测试）
   ├─ engine/      SQL 解析（sqlparse）、EXPLAIN 结果解析
   ├─ local/       本地规则引擎：复杂度评分、schema 读取、13 条规则
   ├─ ai/          AI 引擎（抽象基类 + 工厂 + DeepSeek/OpenAI/Ollama 实现）
   ├─ db/          MySQL 连接器（+ 无数据库时的模拟连接器）
   ├─ optimizer.py 分流路由：本地 or AI
   ├─ diagnostics/ 启动环境自检 + 分层修复
   ├─ index_experiment.py  索引实测（建→测→回滚）
   ├─ report/      性能对比、报告格式化
   └─ coach.py     主编排服务
```

**数据流**

```
SQL → 解析 → 读 schema → EXPLAIN → 复杂度评分 → 分流 ─┬─ 本地规则引擎 ─┐
                                                      └─ AI 大模型 ────┴→ 实测 → Report
```

**关键设计原则**

- **核心零耦合**：GUI 只做展示，所有业务逻辑在核心库；核心库不依赖 Qt，可单独测试
- **契约统一**：本地引擎与 AI 引擎产出同一种 `AnalysisResult`，上层无需区分
- **优雅降级**：无数据库 → 模拟模式；本地引擎异常 → 自动降级到 AI；schema 读取失败 → 保守结论
- **可替换**：新增 AI 引擎只需实现抽象基类 + 在工厂注册

## 五、技术亮点

### 1. 不是所有 SQL 都值得调用大模型

简单 SQL 的模式高度固定（缺索引、`SELECT *`、前导通配符……），用规则就能可靠识别。
本项目对 SQL 做**结构特征评分**（表数、JOIN、子查询、CTE、窗口函数、聚合、`OR` 等），
按分数自动分流：

| 分数 | 等级 | 走向 |
|------|------|------|
| ≤ 3 | 简单 | 本地规则引擎（**毫秒级**） |
| 4 – 8 | 中等 | 本地规则引擎 |
| ≥ 9 | 复杂 | AI 大模型 |

效果：绝大多数日常 SQL 不再需要等待大模型，也不需要 API Key。

### 2. 不止给建议，还要"实测"

工具会对比优化前后的真实耗时与扫描行数。

更进一步：**索引实测模式**会临时创建建议的索引、`ANALYZE TABLE` 后复测、再在 `finally` 中回滚，
给出这个索引的**真实收益倍数**。

### 3. 用数据说话：索引收益取决于选择性

在 10 万行的测试表上做了一次**选择性扫描**，得到如下数据：

| 命中率 | 0.05% | 1.01% | 4.99% | 10% | 20% | 30% | 50% | 100% |
|--------|-------|-------|-------|-----|-----|-----|-----|------|
| 提速 | **52.7x** | **5.25x** | 1.15x | 1.03x | 1.01x | 1.01x | 0.99x | 1.00x |

结论：**索引在选择性约 1%~5% 之间就失效了**——命中率 33% 的列上建索引，即便 EXPLAIN 显示用上了索引
（`type=ref`），墙钟耗时依然和全表扫描持平，因为要回表 3 万多次。

据此给工具加了**收益守卫**：实测提速低于 1.3x 就明确给出"不建议创建"的结论。

> 这是本项目的一个真实发现——很多资料里"加索引提速 50-100 倍"的说法，
> **只在谓词选择性足够高时才成立**。

### 4. 工程质量

- **327 个自动化测试**全绿（含边界与异常路径）
- 采用「实现 → 规格符合性审查 → 代码质量审查」的两阶段流程，审查累计发现并修复了多个真实缺陷
- 关键安全路径有测试保护（索引回滚、索引已存在不误删、探测异常降级等）

### 5. 诚实的设计取舍

- 只做**能静态证明等价**的自动改写；深分页、`OR→UNION`、子查询转 JOIN 等有语义风险的**只给建议不改写**
- 无数据库连接时，索引相关结论会明确标注"未校验"，而不是假装确定
- 正则启发式做不到的事（如相关子查询识别）**宁可移除**，也不留一个双向都会出错的规则

## 六、量化结果

- 测试：**327 个用例全部通过**
- 本地引擎处理简单 SQL：**毫秒级**（对比 AI 的数秒级）
- 索引收益实测（10 万行表）：
  - `amount > 999.5`（命中 0.05%）→ **45.9x**，结论"建议采纳"
  - `status = 'pending'`（命中 33.2%）→ **0.98x**，结论"收益有限，不建议创建"
- 单文件 exe：**82.6 MB**，双击即用

## 七、已知局限（诚实说明）

1. 本地规则是**启发式**的，仍可能漏报或误报（已通过文本清洗、保守策略尽量降低）
2. 复杂度评分同样是启发式，分流不保证最优
3. 索引实测模式需要**建索引权限**，且会短暂改动数据库，因此**默认关闭**，需显式开启
4. 目前只在 **MySQL** 上验证过
5. 复杂 SQL 的优化质量依赖所选大模型的能力

## 八、演示步骤（约 2 分钟）

1. **启动**：双击 `sql-coach-gui.exe`（或 `python main.py` 走命令行）
2. **输入一条典型慢查询**：
   ```sql
   SELECT * FROM orders WHERE status='pending'
   ```
3. **观察结果**：执行计划显示 `type=ALL`（全表扫描）、扫描 10 万行；
   识别出"status 缺索引"与"使用了 SELECT *"；索引建议
   `CREATE INDEX idx_orders_status ON orders(status);`
   并标注**优化引擎 = 本地规则、复杂度 = 简单**
4. **开启索引实测**再跑一次 → 显示"实测提速 0.98x，**不建议创建**"
   （因为该条件命中了 33% 的行，选择性太低）
5. **换一条高选择性的查询**：
   ```sql
   SELECT * FROM orders WHERE amount>999.5
   ```
   → 显示"实测提速 45.9x，**建议采纳**"
6. **导出报告**（Markdown / HTML）

## 九、可能被问到的问题

**Q：为什么不干脆全部用大模型？**
A：三个原因——延迟（数秒 vs 毫秒）、成本、以及大模型**看不到你库里真实的索引情况**。
简单 SQL 的模式固定，规则引擎足够可靠；复杂 SQL 才真正需要模型推理。

**Q：本地规则给出的建议会不会是错的？**
A：有三重保护：① 只做能静态证明等价的自动改写，其余只给建议；
② 能连数据库时会读 `information_schema` 校验真实索引，跳过已存在的索引；
③ 连不上库时，结论会明确标注"未校验"，而不是假装确定。

**Q："提速 50-100 倍"是真的吗？**
A：这个说法**只在谓词选择性足够高时成立**。我在 10 万行表上实测：
命中 0.05% 时提速 52.7x，命中 5% 时只有 1.15x，命中 33% 时基本为 0。
所以工具现在会实测收益并给出"是否值得建"的结论，而不是无脑建议加索引。

**Q：索引实测模式会不会把数据库搞坏？**
A：默认关闭。开启后：索引已存在则跳过（不建也不删）；
所有创建过的索引都会在 `finally` 中回滚；回滚失败会明确报错而不是静默吞掉。

**Q：怎么保证不同 AI 模型都能用？**
A：定义了统一的引擎抽象基类，DeepSeek / OpenAI / Ollama 各自实现；
通过工厂按配置创建。新增模型只需实现基类并在工厂注册，其余代码不用动。
